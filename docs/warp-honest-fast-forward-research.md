# Ускоренное выполнение обязанностей при перемотке

**Актуальный статус:** этот документ сохраняет предыдущие исследовательские раунды. Прямой sync уже
реализован и проверен отдельно, но минутный бюджет не достигнут: 32 слота заняли 2,956 с. Полный
профиль остановлен после провалившегося теста длительностью 12:40. Текущая цель — 8192 слота и
первая следующая транзакция за ≤60 с. Все эксперименты собраны в [журнале](warp-experiments.md),
новые кандидаты и их ограничения — в [исследовании минутного бюджета](warp-one-minute-research.md).
Упомянутые ниже «следующие шаги» относятся к датированным историческим раундам, а не к текущему
плану.

Дата исследования: 2026-09-30. Ниже сохранены выводы до реализации. Последующий запрос разрешил
работу по TDD с тонкими изменениями; новые измерения и фактический статус находятся в
[warp-tdd-results.md](warp-tdd-results.md). Предложенный нативный исполнитель ещё не реализован.

## Повторный разбор после измерений

30 сентября пользователь запросил теоретический цикл с сабагентами. Три направления — зависимости
переходов, измеренный pipeline и контрпримеры корректности — сопоставлены повторно после замера
Gloas `honest-v3`. Новая реализация в этом цикле не добавлялась. Факты измерений находятся в
[отчёте](warp-tdd-results.md#диагностика-gloas-honest-v3): 32 слота за 3,857 с, 11 615 signing jobs
в окне наблюдения, отсутствие CPU throttling. Один запрос на диапазон сам по себе не устраняет эту
работу. Бюджет 25 с / 8192 требует менее 3,052 мс на слот с запасом на следующую транзакцию;
достижение такого срока пока не подтверждено.

**Выбранное направление следующего TDD-шага — прямая доставка настоящих sync contributions внутри
существующего VC/BN с сохранением индивидуальных подписей валидаторов.** 8192 sync selection proofs
и 991 подпись gossip-обёртки — 79,1% jobs в измеренном окне. Эти подписи нужны для выбора и
подтверждения агрегатора, но не входят в итоговый блоковый `SyncAggregate`. Их устранение — более
тонкий первый шаг, чем суммирование секретных ключей. Это доля jobs, не обещанный выигрыш времени.
Proofs готовятся на 64 слота вперёд: перенос вычислений за границу измерения не считается
ускорением. См.
[lookahead](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/validator_client/src/lib.rs#L75)
и
[расчёт proofs](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/validator_client/validator_services/src/sync.rs#L624).

VC остаётся единственным владельцем подписания. Перенос всех обязанностей в новый исполнитель и
передача ключей ему не нужны для проверки этой гипотезы. Общая часть подходит Pectra и Gloas;
интеграция проверяется отдельно для каждого выпускаемого bake.

### Что означает фрейм

Фрейм заканчивается на ближайшей границе эпохи, максимум через 32 слота. Заранее готовятся известные
duties, составы комитетов и независимые подписи: RANDAO по ключу/эпохе/domain, selection proofs для
оставшихся обычных путей по ключу/слоту/subnet/domain. После принятого блока известен root для
следующих подписей. Настоящие EL payloads, block/state roots, долговечная защита slashable-подписей,
imports, Gloas envelopes/PTC и epoch transitions выполняются последовательно. На границе фрейма
обновляются расписания, состав ключей и domains; изменение реестра ключей внутри фрейма тоже должно
инвалидировать зависимый кэш. Фрейм не является атомарной транзакцией: ошибка оставляет явно
указанную подтверждённую позицию, а уже подписанную историю не откатывает.

Знание конечного времени не даёт конечный state root. Даже без пользовательских транзакций меняются
RANDAO, награды, автоматические withdrawals и parent roots; historical roots и checkpoints содержат
реальные промежуточные корни. Формула суммы наград не восстанавливает эту историю. У закреплённого
Gloas часть execution requests применяется дочерним блоком; перенос операций через эпоху меняет
результат. См. закреплённые
[per-slot переходы](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/consensus/state_processing/src/per_slot_processing.rs#L121),
[обработку parent requests](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/consensus/state_processing/src/per_block_processing.rs#L555).

### Sync: полнота прежде ускорения

Найден открытый риск нынешнего пути: доступность всех ключей не гарантирует избрание хотя бы одного
sync-агрегатора в каждом subnet каждого слота. Selection proof выбирает агрегатора случайным
образом; повторные позиции одного ключа не дают независимых попыток. Индивидуальные сообщения
попадают в `naive_sync_aggregation_pool`, а блок формируется из contributions другого operation
pool. Поэтому успешный барьер по выбранным агрегаторам ещё не доказывает 512 участников в следующем
блоке. Это вывод из исходников, а не уже воспроизведённая длинным тестом ошибка. См.
[selection proof](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/consensus/types/src/sync_committee/sync_selection_proof.rs#L48),
[operation pool](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/beacon_node/operation_pool/src/lib.rs#L119).

Минимальная последовательность изменений под тестами:

1. В controlled mode доставлять четыре настоящих contributions из уже проверенных индивидуальных
   сообщений прямо в существующий operation pool, сохраняя точные slot/root, membership и
   fully-valid execution status. Успех фазы требует 128 bits каждого subnet. Проверить случай без
   избранного агрегатора. Публичный gossip-путь не меняется; фиктивный `VerifiedSyncContribution` не
   создаётся. Сам `insert` не проверяет вход: новый приёмник от VC обязан проверять агрегат штатной
   криптографией.
2. Для этого внутреннего пути исключить расчёт ненужных sync selection proofs и gossip-обёрток.
   Обычные validator signatures сохранить. Сравнить block/state roots, экономику и checkpoints;
   независимо воспроизвести историю обычным upstream verifier. Затем измерить оставшуюся стоимость.
3. Если измерения оправдают следующий шаг, внутри того же локального signer заменить изготовление
   contribution на `Sign(Σ multiplicity × secret_key, signing_root)`. До этого — побайтовое
   сравнение с обычной агрегацией. Кэш суммы ключей привязан к точному мультимножеству
   pubkeys/кратностей, не к числу активных валидаторов. Вышедший валидатор может продолжать sync
   duties. Секреты остаются внутри signer и очищаются при завершении срока жизни.

Первые RED-проверки: отсутствие выбранного агрегатора при всех настоящих sync messages;
отсутствующий ключ/неверная подпись запрещают успешный барьер; exit с сохранением sync membership и
последующая смена комитета. Для группового signer дополнительно обязательны повторные позиции,
разные подмножества одного размера, неправильные bits/root/domain и нулевая сумма. Создание каждого
индивидуального gossip-пакета не является обещанием прямого пути; настоящие подписи участников и все
consensus-переходы обязательны.

### Gloas PTC: отдельная граница корректности

Прямой PTC aggregate нельзя просто положить в следующий блок: его голоса должны своевременно влиять
на live forkchoice. Сначала нужны проверенные slot/root, точный PTC с повторными позициями,
действительный envelope и payload/blob availability flags; затем штатное применение голосов к
forkchoice и inclusion. Это видно по отдельным
[apply и insert](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/beacon_node/beacon_chain/src/beacon_chain.rs#L2349).
Первый sync-шаг оставляет PTC штатным. Его будущая оптимизация требует отдельного сравнения
forkchoice **до следующего proposal**, включая отсутствующий/невалидный envelope, duplicate delivery
и границу эпохи. При 64 валидаторах PTC содержит около двух назначений на слот: по текущим данным
его оптимизация не оправдывает большего риска первым шагом.

Это обоснованный путь исследования, не доказанная скорость или готовый алгоритм. Нынешние BN block
production ≈6,38 мс и envelope processing ≈4,06 мс на вызов означают, что одной замены sync signer
недостаточно обещать 25 с. Эти длительности включают текущую реализацию/планирование и не являются
физическим нижним пределом. После каждого тонкого шага нужны измерения под неизменными проверками;
полный новый executor не следует писать до доказательства оставшегося узкого места.

## Исходное предложение

Предлагается общий нативный исполнитель диапазона слотов для всех поддерживаемых профилей. Он
выполняет настоящие обязанности контролируемых валидаторов, строит блоки через настоящий EL,
проводит проверки CL и получает финализацию из включённых голосов. На каждом слоте остаются обычные
mainnet-переходы состояния, награды, withdrawals и обработка очередей.

Экономические параметры не меняются. Предыдущий вариант отдельного bake с другой экономикой отклонён
пользователем и не является направлением реализации.

**Уложиться в нынешние 10,783–11,616 с на 8192 слота со следующей транзакцией пока не доказано.**
Найден конкретный способ уменьшить работу, но нет готового upstream API, который одновременно делает
всё перечисленное и обеспечивает этот срок. Одна замена HTTP-опросов этого не доказывает.

Контроль всех ключей позволяет объединять вычисления. Он не делает будущие block/state roots
известными до выполнения предыдущих переходов. История с блоком в каждом слоте содержит
последовательную зависимость через parent root, execution hash и state root. Работа остаётся
пропорциональной числу слотов; заранее приготовленная цепь не подходит к произвольному состоянию
после деплоя, депозита или консолидации. См.
[state transition](https://ethereum.github.io/consensus-specs/specs/phase0/beacon-chain/#state-transition).

## Где сокращать работу

### 1. Один запрос на диапазон, внутренние события вместо опроса каждого шага

Сейчас `src/consensus.ts:34` продвигает BN/VC отдельными HTTP-вызовами, получает committees,
опрашивает marks, Beacon head и EL/CL agreement. `src/http.ts:19` начинает повторные попытки с
задержки 10 мс. Clock HTTP в `bakes/shared/controlled_clock.rs` закрывает соединение после ответа.
Engine gate находится на хосте; запросы из Docker возвращаются через хост к EL.

Кандидат: Deno отправляет одну команду диапазона; нативный цикл возле Lighthouse выполняет фазы до
подтверждённого завершения работы, используя прямые вызовы/события. EL-соединение и gate находятся в
той же Docker VM, с постоянными соединениями. Завершение фазы означает принятие результата, а не
только постановку задачи в очередь. Реальные сетевые deadlines и JWT сохраняются.

Часы протокола последовательно проходят необходимые точки; ожидание 3/4/6/9 секунд происходит в
виртуальном времени. Следующий слот начинается после завершения обязательных действий текущего.
Конкретные обязанности и их зависимости задаёт адаптер hardfork. Gloas обязательно сохраняет payload
envelopes и PTC, а также свою связь finalized checkpoint с execution parent.

Для первого шага VC сохраняет право подписи и существующую slashing database. Если позднее будет
выбран отдельный signer, передача владения потребует подтверждённого завершения текущих задач;
одновременное подписание одними ключами двумя исполнителями недопустимо. Контейнер не требуется
пересоздавать при каждом warp. Работа с внешним signer потребует отдельного поддержанного пути;
ускорение через локальные ключи к нему автоматически не применимо.

### 2. Настоящая агрегатная подпись сразу для группы ключей

Для одинакового signing root в Ethereum BLS можно вычислить:

`Aggregate(Sign(sk₁, m), …, Sign(skₙ, m)) = Sign((Σ skᵢ) mod r, m)`.

Это вывод из линейности BLS: результат совпадает с суммой отдельных подписей. Кандидат особенно
полезен для sync committee и PTC: вместо подписи каждого уникального ключа и последующего сложения
получается одна подпись на одинаковое сообщение и группу участников. Для различных сообщений нужны
разные группы. Источник:
[BLS draft, CoreSign и proof-of-possession](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-bls-signature-06#section-2.6).

Оптимизация должна находиться внутри signer, владеть только локальными devnet-ключами и сохранять
штатную криптографическую проверку результата. Участники, domain, multiplicity и aggregation bits
должны точно совпадать с правилами выбранного клиента. Slashing checks и запись истории каждого
участника выполняются до выдачи подписи. Ключи и временные суммы не покидают signer; нулевую сумму
надо обрабатывать через штатную агрегацию, не обходя валидацию.

Особенность, проверенная по исходникам: sync committee учитывает повторные позиции одного ключа.
**Закреплённый Gloas тоже допускает повторы PTC:** `get_payload_attesting_indices` сортирует индексы
без dedup, а проверка прямо разрешает дубликаты. Поэтому нельзя переносить сюда dedup из другой
ревизии спецификации. Источники:
[sync aggregate](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/consensus/state_processing/src/per_block_processing/signature_sets.rs#L785),
[PTC indices](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/consensus/state_processing/src/common/get_payload_attesting_indices.rs),
[PTC validation](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/consensus/state_processing/src/per_block_processing/is_valid_indexed_payload_attestation.rs).

Lighthouse сейчас оборачивает `blst`; готового высокоуровневого метода суммы секретных ключей в его
wrapper не найдено. Математическая эквивалентность установлена, реализация и её выигрыш на нашей
машине не проверены. Консервативная альтернатива — параллельные индивидуальные подписи с повторным
использованием hash-to-curve, если это поддержит безопасный библиотечный интерфейс.

### 3. Кэшировать только вычисления с известными входами

- RANDAO reveal зависит от ключа, эпохи и domain; повторно подписывать то же сообщение не нужно.
- Duties, committees и суммы ключей можно готовить заранее в пределах известного расписания.
- Ключ кэша обязан учитывать состав/кратность участников и fork domain. Расписание за пределами
  доступного lookahead пересчитывается по реальному состоянию, включая activation/exit,
  consolidation, effective balances и RANDAO.
- После получения нового block root можно параллельно готовить подписи разных групп. Следующий
  зависимый state transition сохраняет последовательность.

Нельзя предполагать постоянные 64 валидатора с одинаковыми балансами: это сломает именно те e2e,
ради которых нужна сеть.

### 4. Использовать имеющуюся пакетную проверку, не отключать проверку

Lighthouse уже умеет проверять набор подписей через `blst` и импортировать segment цепи, разделяя
его по эпохам. Это точка переиспользования, а не ещё не существующая криптографическая функция:
[batch signatures](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/crypto/bls/src/impls/blst.rs#L36),
[segment import](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/beacon_node/beacon_chain/src/beacon_chain.rs#L3179).

Пакетный import ускоряет проверку уже построенных блоков; он сам их не создаёт. Для генерации с
проверкой целой эпохи потребуется отдельный ограниченный буфер предварительных результатов. Это
более сложный вариант: неподтверждённое состояние нельзя публиковать как проверенное, финализировать
или возвращать пользователю. Сначала следует измерить штатную пакетную проверку внутри одного блока
и её перекрытие с независимой подготовкой. Межблочную спекуляцию нельзя считать готовым безопасным
ускорением.

Slashing database уже имеет транзакционный `check_and_insert_attestations`; использовать его с
включёнными проверками. Историю нельзя просто дописывать после перемотки:
[slashing database](https://github.com/sigp/lighthouse/blob/2d281dfa1b407f7c81cd123954a9fd18ee8f02d2/validator_client/slashing_protection/src/slashing_database.rs#L651).

### 5. Сократить лишнюю подготовку EL, сохранить настоящее исполнение

Изученные Geth строят начальный payload без транзакций синхронно и запускают полную сборку в фоне.
Для заранее закрытого пустого txpool можно исследовать использование уже готового начального payload
без ожидания `Updated payload`. Это требует явной границы приёма транзакций: проверка «txpool был
пуст» сама по себе гонку не устраняет. Принятые до границы транзакции исполняются, новые запросы
ставятся после warp. Готовность при непустом txpool по-прежнему надо подтверждать.

Даже payload без пользовательских транзакций выполняет системные вызовы, withdrawals и очереди
запросов. Нельзя заменять его копией родительского EL state. См.
[Geth payload builder](https://github.com/ethereum/go-ethereum/blob/36b2371c59cd91a9b1da062b3e382f05a6d8687e/miner/payload_building.go#L208)
и
[worker](https://github.com/ethereum/go-ethereum/blob/36b2371c59cd91a9b1da062b3e382f05a6d8687e/miner/worker.go#L96).

Первый кандидат сохраняет Geth без изменений. Если этого недостаточно, отдельно измерять стоимость
повторного исполнения при сборке/import и возможность корректного переиспользования результатов
внутри EL. Это уже возможная доработка Geth, а не обещанная настройка Engine API. Исследованный Geth
master `f8f9bc…` вызывает `InsertBlockWithoutSetHead` для нового payload; кэш локального построения

## Как довести до проверяемого решения

Обязательный порядок уточнён пользователем: **TDD до любого прототипа/изменения реализации**. Полный
контракт, red/green evidence и матрица приёмки находятся в
[warp-tdd-acceptance.md](warp-tdd-acceptance.md). Сначала failing regression, затем реализация и
оптимизация под неизменными проверками. Перечень ниже следует читать с этим порядком.

1. Изолированный прототип критического пути на закреплённых клиентах: 32/256/8192 настоящих слотов,
   постоянные EL-соединения, полный учёт state transition, подписи/проверки, slashing DB, хранения и
   первой последующей tx. Отдельно сравнить обычную и непосредственную агрегатную подпись. Начать с
   этого до расширения публичного API или перестройки всей системы.
2. Зафиксировать одинаковую политику выбора операций и сравнить медленный эталон с быстрым путём:
   block roots, CL state root, EL hashes, balances, participation и финализацию. Затем независимо
   воспроизвести созданные блоки и Gloas envelopes штатными проверяющими путями.
3. Проверять отсутствие **добавленных перемоткой** source/target/sync penalties и inactivity leak,
   все необходимые подписи и финализацию. Простого `slashed == false` недостаточно. Снижение
   CL-баланса из-за законного withdrawal/consolidation не является штрафом; сравнивать переходы с
   эталоном. Warp не может задним числом отменить уже пропущенные обязанности.
4. Обязательные границы: эпоха/смена sync committee, fork domain, activation/deposit, voluntary
   exit, consolidation, withdrawals, неравные balances; для Gloas — PTC с повторными индексами и
   envelope validation. Все активирующиеся ключи должны быть доступны исполнителю; один BN не
   означает владения ключами произвольно внесённых депозитов.
5. Проверить остановку посреди диапазона, сохранение signing history, перезапуск и возврат к VC.
   Возвращать подтверждённую позицию; не объявлять целевой timestamp достигнутым после частичного
   сбоя. Не выдавать ложную атомарность для уже подписанной истории.
6. Принимать по двум последовательным скачкам 8192 слота плюс первая tx на той же машине, сравнивая
   с базой выбранного профиля. Не прятать создание истории в startup, отложенную проверку или долгую
   первую транзакцию. Если срок не достигнут, требование не выполнено.

Исполнитель, контракт API и общие тестовые векторы — общие. Обвязка consensus/Engine API, Gloas
envelopes/PTC и профильные сценарии — адаптеры. Каждый hardfork собирается и проверяется независимо
через существующие `bake` / `test:profile`. Старые immutable bakes сохраняются; нативная возможность
потребует новых сборок каждого поддерживаемого профиля, а не отдельного профиля с другой экономикой.
Общие криптографические тесты не требуют сборки всех клиентов.

Ни один из перечисленных новых сценариев пока не запускался. Исследование обосновывает конструкцию и
точки ускорения; оно не подтверждает достижение целевой скорости или готовность реализации.
