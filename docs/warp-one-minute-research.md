# Исследовательский цикл: честный warp за минуту

2026-09-30. Запрос: 8192 слота вместе с первой следующей транзакцией за ≤60 с, без крупного
переписывания клиента. Критерии честности, экономики, реальных подписей/финальности и failure safety
сохраняются. Реализация клиента в этом цикле не меняется. Исходные результаты — в
[журнале экспериментов](warp-experiments.md).

**Уточнение после первых probes:** пользователь ограничил дальнейший поиск алгоритмами. Количество
потоков и scheduling больше не рассматриваются как оптимизации. Прежние сравнения сохранены как
история измерений; следующий кандидат сравнивается в неизменной среде.

## Бюджет и что уже опровергнуто

Текущий direct-sync: 32 слота за 2,956 с, около 92,38 мс/slot. Для 60 с требуется ≤7,324 мс/slot,
ещё минус первая tx: примерно 12,6-кратное ускорение. Один только выигрыш по числу signing jobs не
является выигрышем во времени. Большой тест, который уже занял 12:40, не запускать повторно без
короткого подтверждения достижимости.

| Наблюдение direct-sync          |  Значение на слот | Как трактовать                                                                          |
| ------------------------------- | ----------------: | --------------------------------------------------------------------------------------- |
| BN block production             |          7,269 мс | Включает подготовку/криптографию/EL и вложенные этапы.                                  |
| BN block processing             |          7,679 мс | Не складывать с вложенными таймерами повторно.                                          |
| Envelope processing             |          3,489 мс | Включает EL; не прибавлять newPayload второй раз.                                       |
| Production process + state root |   0,996 +0,599 мс | Часть обязательной последовательной работы.                                             |
| Import core + state root        |   0,111 +0,620 мс | Небольшой резерв reuse; сам по себе не оправдывает переделку import.                    |
| Sync HTTP / VC sync publish     | 23,000 /44,536 мс | Эти времена вложены/перекрываются; не суммировать.                                      |
| VC signing jobs                 |                76 | 64 из них — индивидуальные sync signatures.                                             |
| Engine getPayload / newPayload  |   1,647 /3,185 мс | Включают transport и реальный EL; gate ожидание готовности отдельно было почти нулевым. |

CPU-снимки за 32 слота: EL 0,338 с, BN 2,792 с, VC 1,098 с. При сохранении всей этой работы и лимите
2 CPU получается условно 43/357/141 с на 8192; это **не нижние физические пределы**, поскольку окна
снимков шире вызова и включают background. Но обещание ускорить всё только устранением HTTP не
обосновано.

Чистый upstream replay 64 слота/4,390 с тоже не floor. В нём нет уже применённого Panda
`weighted_selection`; upstream заново выполняет дорогой Gloas rejection sampling. Persistent
state-структуры уже переиспользуют ветви дерева: гипотеза о полной перехешировке 8192 historical
roots каждый слот не подтвердилась.

### Раунд 5: исполненный изолированный probe

До реализации кандидата сохранён baseline: 11 тестов корректности прошли, но производительность
нарушила заранее выделенный бюджет ≤2 мс на 64 подписи. После этого реализован только
исследовательский MSM helper, без изменения клиента. Его 14 тестов прошли, включая испорченную
подпись на каждой позиции, неверный шаг упаковки коэффициентов, subgroup и нулевую взвешенную PK.

| ARM64, 2 CPU, 32 batches по 64 подписи | Пустой success cache | Заполненный cache с другими roots |
| -------------------------------------- | -------------------: | --------------------------------: |
| General batch, mean                    |            15,592 мс |                         15,065 мс |
| Same-message MSM, mean                 |             3,329 мс |                          4,229 мс |
| Same-message MSM, p95                  |             3,433 мс |                          7,660 мс |

RNG, subgroup checks, упаковка, serialization и заполнение cache включены. Подготовка ключей и
подписей исключена из обоих замеров; это только verification. Выигрыш 3,6–4,7 раза на этом
компоненте подтверждён одним парным опытом. **Компонентный gate остаётся RED**, полный warp не
измерялся. Subgroup diagnostic выполнялся отдельно и не позволяет вычесть своё время из
параллельного MSM. Сохранены
[сырые данные, тесты и обе версии исходников](../reports/warp-tdd/same-message/README.md).

Поэтому временный aggregate signer снова рассматривается как следующий кандидат: та же математически
действительная итоговая подпись, но меньше исходных умножений и проверяемых объектов. Постоянного
кэша секретных сумм не будет. Требуются проверка текущего набора ключей, точных кратностей, обычная
проверка агрегата на BN и тесты удаления ключа. Это исследование, не выбранная для выпуска
реализация. Транспорт и остаточный бюджет разобраны отдельно в
[исследовании worker](warp-worker-research.md).

### Раунд 6: стоимость создания подписей

Отдельный baseline обычного `SK.sign` прошёл 4 теста корректности. На 64 подписи разных очередных
roots получено: serial 19,929 мс; постоянный один worker 20,234 мс; два workers 14,081 мс (p95
27,891 мс). При повторяющемся root два workers дали 10,459 мс, но реальные блоки меняют root. Бюджет
mean/p95 ≤1 мс — RED. Это восемь samples, а pool моделирует scheduling, не весь Rayon/Tokio VC.
[Сырые данные](../reports/warp-tdd/shared-hash/baseline.json).

Проверяется максимально простой shared-H вариант: вычислять публичную точку один раз внутри каждого
batch, затем делать все 64 обычных секретных умножения. Постоянный кэш для этого probe не нужен.
Отдельно исследуется четыре настоящих subnet aggregates через временную сумму ключей; им нужен
другой контролируемый путь доставки, текущие 64 индивидуальных сообщения из одной агрегатной подписи
восстановить нельзя.

Shared-H probe затем исполнен: **7 тестов PASS**, включая byte equality всех подписей и ordinary
verification. На меняющихся roots: serial **10,855 мс**, один worker **10,731 мс**, два workers
**5,508 мс** (p95 **5,634 мс**). Публичная hash-точка вычисляется внутри каждого измеряемого batch;
постоянного кэша нет. Gate ≤1 мс остаётся RED. Даже этот сокращённый signing занимает большую часть
всего бюджета слота, поэтому композиция двух crypto helpers не даёт оснований обещать минуту.
[Кандидат, тесты и исходники](../reports/warp-tdd/shared-hash/README.md).

### Раунд 7: ephemeral aggregate и проверка целого sync path

В фиксированной среде исполнены два парных опыта с реальной BLS-криптографией:

| Форма результата                         | Baseline mean | Candidate mean / p95 | Candidate cold preparation | Gate mean ≤3 мс |
| ---------------------------------------- | ------------: | -------------------: | -------------------------: | --------------- |
| Четыре subnet aggregate по 128 positions |     26,020 мс |     2,331 / 2,458 мс |                   0,307 мс | RED → GREEN     |
| Один full aggregate на 512 positions     |     27,816 мс |     1,563 / 1,612 мс |                   0,266 мс | RED → GREEN     |

Первый baseline прошёл 9 тестов, candidate — 12. Full baseline/candidate прошли по 12 library + 2
CLI теста. До включения каждого candidate сохранён исполненный baseline. Измерение включает live key
lookup, временную сумму scalar с точными multiplicities, подпись, serialization и обязательную
randomized BLS verification результатов. Дополнительные ordinary oracle checks исключены
симметрично. Восемь samples не доказывают длительную tail latency.

Групповые секреты не сохраняются; scratch очищается на success/error/zero/unwind. Проверены byte
equality, изменённые root/domain/key, missing/replaced keys, intermediate zero, zero subnet с
валидным full aggregate, компенсирующие ошибки и non-subgroup. Если subnet sum равен нулю, нужен
fallback **всего batch** к ordinary individual path. Это компонентные проверки; native
pool/admission, restart и post-warp операции ещё не исполнены.
[Исходники, ошибки, RED/GREEN и reproduction](../reports/warp-tdd/group-sync/README.md).

Full aggregate быстрее и использует готовый aggregate_pubkey настоящего state, но требует
дополнительного ограниченного pool entry и fail-closed production guard. После потери entry BN
должен отказать до подписи следующего блока, а не автоматически подставлять пустой SyncAggregate.
Строгий bootstrap и явно разрешённый skip отличаются от произвольного gap. Нынешний
`prepare_controlled_skip` такого разрешения не доказывает.
[Контракт и точки в pinned source](warp-group-sync-research.md).

Этот результат даёт измеренный алгоритмический резерв **только sync-компонента**. Вычитать время
standalone baseline из 92,38 мс live slot как независимый интервал нельзя. Повторные exact BLS
checks и public aggregate PK sums остаются отдельными гипотезами; остаточный serial budget требует
короткого integration measurement до любого длинного запуска.

### Раунд 8: проверка оставшегося алгоритмического бюджета

Независимый повторный разбор не подтвердил скрытый большой резерв SSZ: persistent tree cache уже
переиспользуется. Production/import занимают разные последовательные этапы, но содержащиеся в них
таймеры не складываются повторно. Exact crypto cache может убрать дубли, однако не весь batch
стоимостью одного его элемента. Самое маленькое следующее сокращение — ordinary verify для одного
aggregate вместо general batch1 — имеет лишь ориентир около 0,35 мс, пока без отдельного A/B.
[Полная раскладка, источники и границы вывода](warp-algorithm-budget.md).

При 64 валидаторах PTC и beacon attestations имеют по два distinct signer на слот. Их grouping не
даёт прежнего sync-масштаба 64→1. PTC содержит 512 позиций с повторами; арифметику можно свернуть по
точным кратностям без изменения самих индивидуальных голосов. Новый aggregate admission обязан
сохранять first-valid-vote guard: подпись не разрешает повторному голосу перезаписывать fork choice.
У slashable attestations штатная DB уже batch-проверяет каждый ключ и отклоняет unsafe/SameData;
замена signer затрагивает этот контракт и не выбрана первой оптимизацией.

### Раунд 9: redundant attestation wrappers

Два независимых разбора подтвердили: production обоих pinned клиентов уже переносит проверенные
naive aggregates в обычный operation pool. Поэтому отдельный direct-attestation API, вероятно, не
нужен: можно исследовать удаление controlled selection proofs и локальных aggregate wrappers,
сохранив индивидуальные подписи, slashing DB и штатный packing. Из прежних metrics граница
затронутой VC-работы — около **5,243 мс/slot**, не доказанная экономия whole-slot. Первые две
индивидуальные BLS-проверки (**7,593 мс/slot**) остаются; их cache entries не равны aggregate tuple.

Обнаружено существенное условие: naive insert может пройти после ошибки fork choice, а слишком
старый input может вернуть Ok, ничего не сохранив. Поэтому нужен exact-data/full-participant BN
barrier с подтверждённым FC, затем проверка реального packed block; publication mark или полные pool
bits сами по себе недостаточны. Restart, pruning и split Gloas index также остаются гейтами. TDD
должен сначала показать, что upstream inclusion без wrappers уже работает, и найти RED в новом
требовании readiness/отсутствия лишней работы, а не выдумывать broken baseline.
[Алгоритм, измерения и точные native критерии](warp-attestation-research.md).

## Основной кандидат: та же история, меньше повторной работы

### 1. Same-message randomized batch

Все 64 sync-голоса конкретного слота подписывают одинаковый полный signing root. Текущий
`verify_multiple_aggregate_signatures` обрабатывает их как общий случай разных сообщений: повторяет
hash-to-curve и добавляет отдельные Miller-loop вклады. В библиотеке также есть
`fast_aggregate_verify` для общего сообщения, но он проверяет агрегат и не доказывает корректность
каждой исходной подписи. Вместо этого для фиксированного набора входов генерируются свежие
независимые ненулевые коэффициенты `r_i`, после чего вычисляются:

```text
P = Σ r_i · PK_i
S = Σ r_i · signature_i
verify(S, P, signing_root)
```

Это две публичные MSM и одна BLS-проверка, в которой остаются две Miller-loop пары. Индивидуальные
подписи и membership не заменяются «подписями от имени сети». Проверка каждой подписи на subgroup
проходит до MSM. Смешанные signing roots используют прежний batch. Вырожденный weighted PK/infinity
не является успехом; нужен штатный fallback. Exact positive-cache заполняется только после успеха
всего batch. Модель случайной проверки такая же вероятностная, как у текущего upstream.

**Критическая регрессия:** при `nbits=64` MSM читает 8 байт на коэффициент. Нельзя передать подряд
32-байтные `blst_scalar`: тогда большая часть коэффициентов станет нулевой и испорченные входы
исчезнут из проверки. Тест меняет по очереди каждую из 64 позиций. Другие отрицательные сценарии:
переставленные подписи, компенсирующие ошибки, неверный root/DST, чужая subgroup, infinity, пустой
batch и дубликат pubkey с другой подписью. Простая сумма без случайных коэффициентов неприемлема.

Локальная точка изменения — существующий `bakes/shared/native/verified_signature.rs`, без нового
consensus state transition. Сначала изолированный harness. API проверен для Gloas blst 0.3.17;
Pectra blst 0.3.14 требует отдельной проверки совместимости.

Первичные источники:
[pinned Rust API и test_multi_point](https://raw.githubusercontent.com/supranational/blst/v0.3.17/bindings/rust/src/lib.rs),
[pinned C aggregation](https://raw.githubusercontent.com/supranational/blst/v0.3.17/src/aggregate.c),
[BLS CoreSign/Aggregate](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-bls-signature-06).

### 2. Сохранить 64 подписи, один раз вычислять общую публичную часть

Для одного root вычислить публичную `H(root)` один раз, затем выполнить обычное секретное умножение
каждого ключа. Кэш ограничен, хранит только публичные точки и весь криптографический контекст;
первый промах имеет single-flight, lock отпускается до умножений. Секрет не надо сериализовать: blst
предоставляет ссылку на scalar. Существующие key lookup, signing jobs и slashing flow сохраняются;
каждая подпись должна побайтно совпадать с обычной.

64 scalar multiplications и 64 Rayon jobs остаются. Публичный MSM не является заменой 64 подписей и
не должен применяться к секретным коэффициентам. Это кандидат для measured probe, не обещанное
ускорение в 64 раза.

### 3. Проверять один и тот же криптографический факт один раз

Существующий bounded one-key success-cache уже дал измеренный выигрыш. Дополнительный кандидат —
использовать его и в `verify_signature_sets`, где сейчас блок заново проверяет signatures, ранее
проверенные в gossip. Ключ: точные `(aggregatePK, signingRoot, signature)` при фиксированных
algorithm/DST. Отдельный публичный aggregatePK-cache строится по точному набору и кратностям ключей.
Смена membership/slot/root, coverage и структура по-прежнему проверяются обычным кодом.

Создание подписи само по себе не является проверкой; нельзя заранее заполнить cache успехом только
потому, что объект создан локально. Готовый production-state тоже не подтверждает все подписи:
`ProduceBlockVerification::VerifyRandao` проверяет лишь RANDAO. Штатный
`SignatureVerifiedBlock::new` действительно создаёт private witness после проверки подписей.

### 4. Исторический transport-вариант — дальнейший поиск остановлен

**После уточнения пользователя этот вариант больше не исследуется.** Ниже сохранены прежние
наблюдения, а не действующий план. Crypto-only пока не гарантирует минуту. Сейчас пять фаз × два
clock endpoint, а clock HTTP закрывает каждое соединение. В историческом v3 trace все 352 вызова
clock заняли суммарно 433,001 мс за 32 слота, то есть 13,53 мс/слот. Среднее 1,23 мс на вызов
объединяет GET и POST; стоимость именно десяти advances отдельно не измерена. Это исторический
trace, не измерение новой topology.

Отдельный риск — polling в `src/http.ts::waitFor`: после первого ответа not-ready или ошибки
планируется 10 мс реального sleep, если до deadline осталось достаточно времени. Это уже больше
среднего бюджета 7,324 мс на слот, если такой промах возникает на последовательном пути каждого
слота. Фактическая частота пока не измерена; последующие паузы растут до 250 мс. В коротком probe
нужно записать attempts, причины not-ready и фактический sleep по каждому месту ожидания, отдельно
для head, EL/CL agreement и первой tx. Быстрый transport может лишь раньше попасть в not-ready,
поэтому перенос worker сам по себе не устраняет этот риск и не доказывает достижимость минуты.

Предпочтительнее сначала исследовать owned TS worker внутри Docker-сети с тем же `Timeline`,
`Consensus` и `Automine`. Host сохраняет lifecycle и публичнуюlocalhost-границу, worker — один
владелец advancement и локального RPC/automine notify. Он не получает Docker socket и validator
keys. Все time-методы и отправки транзакций идут через одного владельца; иначе возникнет второй
Timeline и гонки automine. Перенос не должен копировать Controller/consensus logic.

Дополнительный узкий Engine-hook: прямой BN→EL для FCU/newPayload, а существующий hostgate оставить
для `getPayloadV*` и доказанной full-payload readiness. Перед FCU в controlled CL отфильтровать
future attributes по настоящему controlled clock, **до** payload-id cache. Нельзя заранее разрешить
время конца warp: это меняет поведение паузы/expiry. JWT и реальные deadlines сохраняются. Пустой
txpool не используется как оправдание для раннего неподготовленного payload.

Вызовы transition, state roots, Geth execution, envelope/PTC, storage и fork choice остаются
штатными. Это изменение размещения и небольшие hooks; перенос ключей в BN, ручное построение
`BlockImportData` и новый consensus executor выходят за выбранную тонкую конструкцию.

## Что не выбираем первым

- Постоянные групповые секретные ключи: опасная invalidation при DELETE/add/смене committee.
  Временная weighted-сумма через действующие local keys уже прошла компонентный probe; новое
  admission/pool взаимодействие и native failure tests остаются обязательными перед интеграцией.
- Кэш production post-state ради пропуска import transition: измеренные import core + state root
  занимают около 0,73 мс/слот. Это оценка потенциального резерва, а не измеренный выигрыш reuse;
  вмешательство в import/finality/storage существенно.
- Скачок по формуле только от начала и конца: RANDAO, parent roots, withdrawals, finality-gated
  deposits и Gloas parent execution requests зависят от реальных промежуточных переходов.
- Пропуск проверки подписей, искусственные participation/rewards/finality, deferred history или
  медленная первая tx: нарушают исходный контракт.

## Раннее опровержение и TDD

1. Зафиксировать baseline отдельного crypto harness: 64 действительные подписи, настоящие subgroup
   checks, RNG, упаковка, cache/serialization включены. Выделенный предварительный бюджет sync
   verification — ≤2 мс на слот из общего 7,324 мс. Это компонентная гипотеза бюджета, не
   доказательство полного 60 с. Сначала исполнить baseline, сохранить результат, только затем писать
   candidate.
2. Проверить отрицательные входы и differential equivalence. Сравнить 1/2/64/512 входов, cold/warm,
   одинаковые/разные roots; отдельно показать signing и verification. Build error не является RED.
3. Если probe даёт нужный резерв, только тогда тонкая интеграция с теми же
   W03/W04/W06/W07/W08/W15/W18 проверками. Первая live ступень — 32 слота+tx; следующая 256.
   Трассировать последовательные и перекрывающиеся этапы, не суммировать nested timers. Для
   `waitFor` измерять attempts и фактический sleep, для clock — отдельно GET/POST и endpoint.
4. Ранний gate: `setup + steady_slot_cost ×8192 + first_tx ≤60s`, учитывая реальные переходы эпох и
   комитетов. Простая линейная оценка 32→8192 — только предварительный отсев, не приёмка. При
   превышении без конкретного измеренного резерва — остановить этот вариант до длинного запуска.
5. Только после этого два 8192-перехода, реальный deadline ≤60 с вместе с первойtx, полный профиль
   каждого выпускаемого hardfork. Исторические reward/state проверки фиксировать до pruning или
   проверять replay. Pectra отдельно, не за счёт Gloas GREEN.

**Статус:** same-message MSM и shared-H дали ускорение, но остались RED по своим бюджетам. Ephemeral
sync aggregates достигли component GREEN: четыре — 2,331 мс, один — 1,563 мс. Время всей сети ≤60 с
не доказано; клиент не менялся. Следующий round проверяет оставшийся алгоритмический бюджет, PTC и
точный reuse проверенных BLS inputs, без исследования потоков.
