# Форк внешней сети в zap-net

Исследование от 29 сентября 2026 года, код zap-net на `9078f84`. Проверены текущая архитектура,
локальные исходники закреплённых Geth и genesis-generator, документация Hardhat/EDR и первичные
источники Ethereum. Прототип форка и проверки на внешнем RPC в рамках исследования не запускались.
Приведённые сроки — инженерная оценка для одного разработчика, знакомого с клиентами Ethereum.

**Вывод:** форк контрактного состояния через готовый EVM runtime сравнительно прост. Лёгкий форк по
RPC с настоящими Geth, Lighthouse, подписями и финализацией — существенное расширение клиента.
Существующая перемотка времени пригодна для такого режима; главный риск находится в хранении и
изменении состояния EL. Реализация через готовую базу EL проще, но требует значительно больше диска
и подготовки данных.

| Вариант                                                     | Первый прототип                          | Версия с регрессиями         | Что получаем                                                                      |
| ----------------------------------------------------------- | ---------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------- |
| Отдельный EVM-only backend на Hardhat/EDR                   | 2–4 рабочих дня                          | 1–2 недели                   | Форк по URL, локальные изменения и управление timestamp; без нашего настоящего CL |
| Shadow fork из готового состояния Geth + новый локальный CL | 3–5 рабочих дней                         | 2–4 недели                   | Настоящие клиенты, локальные валидаторы и время; тяжёлая исходная база            |
| Подгрузка состояния по RPC внутри Geth + локальный CL       | 1–2 недели после проверки осуществимости | 6–12+ недель                 | Целевой лёгкий режим; высокая неопределённость вокруг trie/proofs и провайдера    |
| Продолжение исходного BeaconState с его валидаторами        | Отдельное исследование                   | Обоснованного срока пока нет | Требует решения вопроса ключей, состояния валидаторов и планировщика              |

Оценки предполагают одну заранее выбранную Ethereum L1-сеть и совместимый Pectra-блок, без
универсальной поддержки L2, произвольных hardforks, impersonation и snapshot/revert всей EL/CL. Для
варианта с базой её получение, скачивание и синхронизация считаются отдельно. Для лёгкого варианта
сначала нужен исследовательский этап на 3–5 рабочих дней; отрицательный результат может потребовать
другого upstream API или другого подхода, а не просто больше времени.

**Что означает «как в Hardhat».** На выбранном блоке фиксируется исходное состояние. Данные
аккаунтов, кода и storage подгружаются при обращении, затем изменения хранятся локально. Фиксация
блока делает тест воспроизводимым и позволяет повторно использовать кэш. Это описано в
[руководстве Hardhat по форкам](https://v2.hardhat.org/hardhat-network/docs/guides/forking-other-networks)
и [актуальном руководстве Hardhat 3](https://hardhat.org/docs/guides/forking).

Hardhat использует EDR; его модель не требует консенсуса и P2P. Поэтому обычный fork-тест контрактов
не воспроизводит работу Beacon Chain, активацию валидатора и голосование за финализацию. См.
[объяснение модели EDR](https://hardhat.org/docs/explanations/edr-simulated-networks) и
[реализацию EDR](https://github.com/NomicFoundation/edr).

**Что уже подходит в zap-net.** В [network.ts](../src/network.ts) Docker lifecycle отделён от
выполнения слотов; [time.ts](../src/time.ts) сериализует продвижение времени;
[consensus.ts](../src/consensus.ts) проверяет согласованность реальных EL/CL;
[engine.ts](../src/engine.ts) управляет подготовкой payload. Эти части можно переиспользовать.

Сейчас `Network.startOwned` всегда создаёт пустые volumes, генерирует genesis и запускает
`geth init`. Начальные 64 валидатора принадлежат нашему VC. Существующий режим не умеет подключать
исходный блок или читать отсутствующий storage из другого узла. Слова `engine_forkchoiceUpdated` в
Engine API означают выбор ветки консенсуса; они не включают режим форка по внешнему RPC.

**Почему одного RPC-прокси недостаточно.** При исполнении транзакции Geth читает storage через
`StateDB`, включая вложенные вызовы и `delegatecall`. Перенаправление внешнего `eth_call` на mainnet
не обеспечит выполнение следующей локальной транзакции над смешанным исходным и изменённым
состоянием. Нужны чтение исходного состояния внутри EL, локальные записи и корректный новый
`stateRoot`.

Это подтверждается закреплённым кодом Geth v1.15.11:
[Database/Trie](https://github.com/ethereum/go-ethereum/blob/v1.15.11/core/state/database.go),
[state readers](https://github.com/ethereum/go-ethereum/blob/v1.15.11/core/state/reader.go),
[StateDB](https://github.com/ethereum/go-ethereum/blob/v1.15.11/core/state/statedb.go). Локальный
checkout проверен: `36b2371c59cd91a9b1da062b3e382f05a6d8687e`. В нём нет готового RPC fallback в
этом пути. Для выбранной архитектуры ленивую подгрузку придётся добавлять в Geth либо разрабатывать
совместимый execution backend.

**Самый сложный технический участок — proofs и запись состояния.** Вариант для исследования:
прикрепить частично загруженное дерево к `stateRoot` исходного блока, получать код и proofs,
проверять их, хранить полученные узлы локально и выполнять обычные переходы состояния Geth.
[EIP-1186](https://eips.ethereum.org/EIPS/eip-1186) даёт account/storage proofs относительно корня
выбранного блока. Локальные записи должны иметь приоритет, включая явный ноль и удаление; нельзя
после записи нуля повторно подставлять старое значение из upstream.

Однако proof отдельного ключа не гарантирует наличие всех узлов, необходимых для изменения дерева. В
`trie.go`, в ветке удаления из `fullNode`, Geth может разрешать оставшийся соседний узел для сжатия
ветки. В `state_object.go` комментарий прямо описывает этот случай при удалении storage. Значит,
обычный `eth_getProof(address, [slot], block)` может оказаться недостаточным: нужно доказать
получение дополнительных узлов или определить дополнительный интерфейс источника. Это конкретный
риск для прототипа, а не подтверждённая готовая архитектура. Источники:
[удаление из trie](https://github.com/ethereum/go-ethereum/blob/v1.15.11/trie/trie.go),
[обновление storage](https://github.com/ethereum/go-ethereum/blob/v1.15.11/core/state/state_object.go).

Отдельно проверяется способность провайдера отдавать **исторические proofs**. Наличие исторического
`eth_call` ещё не доказывает такую способность. Например, документация Geth различает хранение
исторических значений и trie-узлов: для path-based archive исторические proofs появились в v1.17.x
при соответствующей настройке `history.trienode`. См.
[документацию archive mode](https://geth.ethereum.org/docs/fundamentals/archive).

**Уже существующий путь без изменения Geth — shadow fork.** В закреплённом genesis-generator v4.0.0
обнаружены `SHADOW_FORK_RPC`, `SHADOW_FORK_FILE` и передача
`--shadow-fork-block`/`--shadow-fork-rpc` в `eth-beacon-genesis`. Проверенный commit:
`f06b98c2cb789c6ac45fd0e6167173820dc095d2`, файлы `entrypoint.sh:95` и `defaults/defaults.env:33`.
Генератор может связать новый CL genesis с выбранным EL header.

Но этот параметр не скачивает состояние контрактов в пустую базу Geth. Нужен согласованный
снимок/подготовленная база EL с состоянием выбранного блока. Именно такой подход описан в
[руководстве Ethereum по shadow fork](https://notes.ethereum.org/@parithosh/shadowfork-tutorial) и
[материале ethPandaOps](https://ethpandaops.io/posts/kurtosis-deep-dive/). Полный archive всей
истории не обязателен: нужен доступный state выбранной точки и необходимые данные цепи. Обычный
[snap sync Geth](https://geth.ethereum.org/docs/fundamentals/sync-modes) всё равно загружает
состояние сети; по стоимости это другой режим, чем адресная подгрузка Hardhat.

Работы в zap: импортировать копию базы в owned volume, проверить block hash/state root, сохранить
совместимый EL genesis и расписание forks, сгенерировать новый CL, настроить время, проверить первый
payload и финализацию. Исходную базу открывать только для чтения или копирования. Учитывать
завершённую запись базы, формат клиента и finalized/safe markers; перенос одного `latest_block.json`
не является переносом базы. Kurtosis подключать для этого не требуется.

**Валидаторы определяют границу возможностей.** Форк execution state переносит контракты, балансы и
storage. Он не переносит автоматически BeaconState: validator indices, BLS-ключи, activation/exit
epochs, pending queues, balances и историю финализации.

С новым локальным CL можно сохранить настоящие депозит → активация, voluntary exit → withdrawal и
consolidation для локальных ключей. Потребуется согласовать реальный адрес deposit contract, его
счётчики и границу старых депозитов с новым CL, параметры сети и существующие системные очереди. У
zap сейчас deposit contract по умолчанию `0x4242…4242`; такой адрес нельзя молча сохранить при
подключении произвольной публичной сети.

На уровне EL нужны штатные обработки EIP-4788/2935 и Pectra requests; pinned
`core/state_processor.go` вызывает обработку депозитов, withdrawals и consolidation. Источники:
[state processor](https://github.com/ethereum/go-ethereum/blob/v1.15.11/core/state_processor.go),
[EIP-6110](https://eips.ethereum.org/EIPS/eip-6110),
[EIP-7251](https://eips.ethereum.org/EIPS/eip-7251).

Существующие mainnet staking-контракты могут хранить ссылки на валидаторов и результаты оракулов
исходной сети. Новый локальный CL не делает эти ссылки согласованными автоматически. В частности,
Lighthouse игнорирует consolidation request, если source/target pubkey отсутствует в его реестре
(`process_operations.rs`, `process_consolidation_request`). Перенести исходный BeaconState
недостаточно: без соответствующих signing keys мы не можем просто продолжить штатные proposals и
attestations. Замена набора ключей создаёт явно преобразованное состояние. Текущие barriers также
предполагают владение всем набором валидаторов. Это отдельный объём работ.

**Перемотка времени сохраняется.** Для ветки от блока B надо выбирать начальные часы относительно
`B.timestamp` и обеспечить допустимый timestamp первого потомка. Использование текущего default 2033
года без обсуждения немедленно состарит time-sensitive контракты. Обычные `advanceTime` и
`advanceTo` должны продолжить обработку всех промежуточных слотов; `skipSlots` остаётся отдельной
операцией. Переход на форк не должен незаметно менять эту семантику на один EVM timestamp jump.

Скорость на холодном кэше будет зависеть от upstream RPC, числа чтений, лимитов и proofs. Уже
измеренные 8,85 с на 20 локальных деплоев нельзя переносить на новый режим. Нужны отдельные замеры с
холодным и прогретым кэшем. Зафиксированный block hash/state root обязателен: локальные записи не
должны смешиваться с продолжающим меняться upstream `latest`.

**Совместимость с остальными удобствами Hardhat.** Полный parity включает impersonation,
setBalance/setStorageAt, reset, snapshot/revert. Эти операции не входят автоматически в форк
состояния. Hardhat поддерживает impersonation без приватного ключа; штатный Geth не может подписать
валидную транзакцию чужого EOA без ключа. Обход проверки подписи противоречит текущему требованию
zap. Для настоящего EL/CL сначала использовать управляемые аккаунты и явно описанные начальные
fixtures; изменение этой границы требует отдельного решения.

EDR как отдельный backend позволяет быстро получить контрактный fork-режим, но он меняет требование
к реальному CL и не должен подменять существующие validator e2e. Anvil также нельзя считать готовой
подключаемой заменой Geth для Lighthouse: на дату проверки запрос
[Engine API в Anvil #5994](https://github.com/foundry-rs/foundry/issues/5994) открыт. Это сигнал
необходимости отдельной проверки совместимости, а не доказательство работоспособности адаптера.

**Предлагаемый первый этап на 3–5 рабочих дней.** Зафиксировать семантику: внешний EL state, новые
локальные валидаторы, один поддерживаемый hardfork, настоящие подписи и forward-only time.
Подготовить небольшой полностью известный state fixture и удалённый источник для него.

1. Воспроизвести чтение, изменение и обнуление storage над частичным trie. Сравнить каждый новый
   root с обычным Geth, у которого полный исходный state; включить удаление с коллапсом ветки.
2. Проверить RPC-провайдер: pinned block hash, code hash, отсутствие аккаунта/слота, исторические
   proofs, получение недостающих соседних узлов, timeout/429 и отсутствие смешения блоков.
3. Проверить системные вызовы Pectra, `eth_call`/estimateGas/реальный send, proxy/delegatecall,
   revert и повторное чтение изменённых значений после следующего блока.
4. Если первые проверки проходят, связать исходный EL header с локальным CL genesis, получить
   валидный первый payload и проверить forward-time. Полный validator e2e и финализация — критерии
   следующего этапа, не подмена их успешным `eth_call`.

После этого можно подтвердить либо пересмотреть оценку 6–12+ недель. Если обычный RPC не даёт
достаточного witness для корректных обновлений, выбрать расширенный источник данных или shadow fork
с готовой базой. Для пользователя, которому достаточно контрактного форка, отдельный EDR-режим
остаётся более коротким путём, но не решает задачу реального staking e2e.

Для MVP также понадобятся fork manifest без RPC-секретов, cache key по chain/genesis/block hash,
ограничение диска, воспроизводимый reset, раздельные local/upstream logs и receipts, обработка
`BLOCKHASH`, совместимый chain ID и тест funding. Привязка контракта к chain ID, EIP-712 и
историческим Beacon roots требует отдельных fixtures. Текущая проверенная сеть ограничена
Prague/Electra; более новые исходные блоки требуют отдельного обновления клиентов и повторной
проверки Lighthouse patch/EngineGate. Поддержка любой сети через один URL пока не обоснована.
