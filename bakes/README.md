# Устройство бейкеров

Каждый хардфорк хранит свои входы сборки и дополнительные тесты в одной папке. Общий сборщик —
[`src/baker.ts`](../src/baker.ts); общий тип `Recipe` и явный реестр —
[`src/profiles.ts`](../src/profiles.ts).

```text
bakes/
  shared/
    controlled_clock.rs
    controlled_clock_test.rs
    native/                   # общие Rust helpers и их нативные регрессии
    patch_bls.py              # общая часть инструментов patch.py
    patch_direct_sync.py      # прямая доставка проверенных sync-голосов
    tests/                    # общие e2e и fixtures
  pectra/
    recipe.json
    lighthouse.patch
    patch.py                  # инструмент сопровождающего, не шаг обычного bake
    tags/                     # готовые сборки по тегам
    release/clients.lock.json # выбранный опубликованный комплект для релизов Panda
  gloas/
    recipe.json
    lighthouse.patch
    patch.py
    native/                   # дополнительные Rust-исходники этого профиля
    tests/                    # envelope/PTC и другие профильные проверки
    tags/
```

Профиль является **стратегией, заданной данными**. Общие часы и тесты подключаются **композицией**:
рецепт ссылается на их файлы. Последовательность pin → snapshot → prepare → native tests → compile →
publish реализована один раз. Иерархии классов и отдельной копии сборщика на каждый fork нет.

| Файл/папка                             | Назначение                                                                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `<hardfork>/recipe.json`               | Совместимые версии EL/CL/genesis, toolchain, paths, Engine/phase metadata и явная карта сценарий → файл.                                   |
| `<hardfork>/lighthouse.patch`          | Проверенный patch к закреплённому upstream commit.                                                                                         |
| `<hardfork>/native/`                   | Дополнительные исходники, если нужны; входят в хеши сборки.                                                                                |
| `shared/native/`                       | Helpers, которые используют несколько профилей; подключаются их патчами и nativeTests.                                                     |
| `shared/tests/`                        | Общие исполняемые сценарии и вспомогательные модули, без копирования по профилям.                                                          |
| `<hardfork>/tests/`                    | Только дополнительные сценарии конкретного профиля. Пустая папка для симметрии не нужна.                                                   |
| `<hardfork>/tags/<tag>.json`           | Готовый immutable manifest с источниками, хешами и image IDs; его создаёт baker.                                                           |
| `<hardfork>/release/clients.lock.json` | Выбранный опубликованный комплект amd64: исходный bake и registry digest Lighthouse. Создаётся `clients:pin` из результата клиентского CI. |

Корневая `tests/` содержит быстрые unit-тесты и общие проверки Docker/baker. Отчёты находятся в
`reports/profiles/<hardfork>/<tag>/`. Третьесторонние исходники, архивы входов, compiler caches и
артефакты сборки находятся в игнорируемой `.cache/baker/`.

Lighthouse публикуется отдельным workflow с тегом `v<upstream>-<commit>-b<bakerVersion>-<hash>`.
Поля `clVersion`, `clRef` и `bakerVersion` задаются в рецепте. Хеш входов бейкера учитывает его код,
патчи, часы и закреплённое окружение; изменение контроллера не меняет версию Lighthouse. Релизы
Panda получают версию из Git-тега `vX.Y.Z` и используют закреплённый комплект без компиляции
клиентов. Файл выбора появляется после первой реальной публикации; подробности — в
[руководстве CI](../docs/ci-containers.md).

`sourceFiles` фиксирует дополнительные native-входы в хешах и архиве. Их подключение к upstream
обеспечивает проверенный патч; добавление файла в список само по себе не включает его в Rust build.
`patch.py` используется сопровождающим при подготовке патча и не исполняется автоматически при
обычной сборке. Общий clock source и его тест сборщик устанавливает отдельно из снимка входов.

Возможности бинарника указываются в рецепте и сохраняются в immutable manifest. Например,
`clockWait: true` включает ожидание фактических phase marks через нативное уведомление с реальным
таймаутом. Контроллер читает capability выбранного тега; старые теги продолжают использовать
polling. Изменение текущего рецепта не включает новую возможность в уже собранном образе.

`directSync: true` объявляет controlled-only доставку полных sync contributions из уже проверенных
индивидуальных сообщений в обычный operation pool. VC сохраняет ключи и обычные подписи, но не
вычисляет sync selection proofs и подписи gossip-обёрток. BN подтверждает все позиции четырёх
подкомитетов отметкой для конкретного slot/root. Контроллер связывает её с той же головой, для
которой уже подтверждён execution. При неполном участии возникает ограниченная ошибка; отметка VC
сама по себе не считается подтверждением. Часы хранят только последний root этой фазы.

Gloas может доставить голоса до envelope: помещение в candidate pool не подтверждает EL validity.
Штатные проверки блока, envelope, PTC и защита slashable-подписей сохраняются. Native-регрессия
`beacon_chain/panda_direct_sync` использует pre-merge компонентную фикстуру без EL; совместимость
настоящих EL/CL проверяется отдельным выбранным `test:profile`.

## Изменить версию в существующем профиле

```sh
deno task bake gloas --tag candidate --cl-ref <commit> --patch bakes/gloas/lighthouse.patch
deno task test:profile gloas --bake candidate
deno task up --profile gloas --bake candidate
```

Новый тег использует тот же профиль. `up` не компилирует клиентов. Полный список overrides и
особенности артефактов — в [руководстве по версиям](../docs/bakes.md).

## Добавить хардфорк

1. Создать `bakes/<hardfork>/recipe.json` по существующему профилю. Указать совместимые pins,
   toolchain, расписание, Engine-версии и пути к общим исходникам. Добавить только необходимые
   собственные патчи/native helpers.
2. В `tests` явно указать имена отчётов и файлы сценариев. Общие сценарии подключать из
   `bakes/shared/tests/`; новые проверки разместить в папке профиля.
3. Добавить импорт рецепта и одну запись в `profiles` в `src/profiles.ts`. Общий сборщик менять не
   требуется. Если сам протокол меняет Engine/Beacon поведение, сначала добавить failing tests,
   затем соответствующую поддержку runtime — декларация рецепта её не заменяет.
4. Выполнить `deno task check`, быстрые тесты, `bake <hardfork> --tag <tag>` и
   `test:profile <hardfork> --bake <tag>`. Native-тесты входят в сборку; повторный запуск для
   готового артефакта: `test:clock <hardfork> --bake <tag>`.

Изменение одного профиля не требует сборки остальных. Fingerprint тестов включает только выбранную
карту сценариев и её исполняемые зависимости. Изменения общего runtime требуют проверки каждого
выпускаемого с ними профиля; общие Docker/baker-проверки запускаются отдельно через `test:baker`.

## Совместимость с прежним расположением

Девять исходных манифестов перемещены из `<hardfork>/<tag>.json` в `tags/` без изменения байтов. Их
keys, image IDs и старые hash keys сохранены. Native-тесты используют точные архивы bake;
восстановление из перенесённого рабочего файла возможно только при совпадении исходного хеша.

Reader также понимает старое расположение локальных тегов. Различающиеся копии одного тега в двух
местах отклоняются. Одинаковые копии читаются, но перед `--replace` нужно оставить одну. Для
legacy-only тега замена сохраняет его прежний путь и атомарность записи. Новые теги создаются в
`tags/`. Имя тега `recipe` не конфликтует с определением профиля.

Изменившиеся пути тестов меняют suite fingerprint: старые результаты остаются историческими; текущий
`verified` появляется после реального запуска нового набора. Это не меняет бинарники.
